# Угадай мелодию — локальная версия v1.5.1

Приложение ведущего для игры «Угадай мелодию» на React + Effector + TypeScript + Vite.



## Изменения v1.5.1 — многоэтапный межраунд «4 трека»

- межраунд **«4 трека — общая тема»** теперь может содержать несколько этапов; каждый этап имеет собственные 4 аудиотрека, ответы и общую тему;
- после показа ответов одного этапа ведущий переходит к следующему, а последний этап завершает межраунд;
- прогресс сессии хранит отдельно номер этапа и номер текущего трека, поэтому перезагрузка восстанавливает точное место;
- старые межраунды шаблона `commonTheme4` v1 автоматически мигрируют в `templateVersion: 2` с одним первым этапом;
- `.melody` повышен до **formatVersion 4**, импорт архивов v1–v3 сохранён;
- кнопки изменения порядка раундов/межраундов получили компактные SVG-chevron controls вместо системных символов `↑/↓`.

## Изменения v1.5.0 — библиотека межраундов

- в конфигурации игры появился единый порядок `stages[]`: обычные раунды и межраунды теперь являются последовательными этапами игры и могут переставляться вверх/вниз;
- добавлена отдельная мини-библиотека готовых шаблонов межраундов; первый релиз содержит **«Продолжи песню»** и **«4 трека — общая тема»**;
- каждый шаблон имеет собственную строго типизированную конфигурацию, правила, редактор и player, а общая платформа отвечает только за lifecycle и порядок этапов;
- перед каждым межраундом всегда показывается отдельный экран с правилами; баллы ведущий начисляет вручную через существующее табло команд;
- **«Продолжи песню»** поддерживает несколько заданий: выбор `MediaTrack`, момент остановки, количество следующих слов и текст правильного ответа; после остановки ответ открывается только по команде ведущего, а на экране ответа исходный трек воспроизводится целиком с самого начала;
- **«4 трека — общая тема»** хранит ровно четыре `MediaTrack`, правильное название/исполнителя каждого и общую тему; прогресс прослушивания четырёх треков сохраняется в игровой сессии;
- межраунды используют `MediaTrack` напрямую и не создают фиктивные `Song`; внутренние названия медиатреков не показываются игрокам и не могут случайно подсказать ответ;
- удалить `MediaTrack`, который используется межраундом, нельзя; экспорт игры автоматически включает треки/Blob, используемые только межраундами;
- `.melody` повышен до **formatVersion 3**. Архивы v1 и v2 продолжают импортироваться: старым играм автоматически создаётся последовательность обычных этапов, а старый `roundIndex` сессии мигрирует в `stageIndex`;
- локальная схема состояния повышена до v4, IndexedDB — до версии 5; существующие игры и сохранённые партии мигрируют автоматически.

Текущая модель игровой структуры:

```text
GameConfig
  stages[]
    ├─ Round stage ──> Question ──> Song ──> MediaTrack ──> AudioAsset
    └─ InterRound stage ────────────────> MediaTrack ──> AudioAsset

InterRound templates
  ├─ continueLyrics
  └─ commonTheme4
```


## Изменения v1.4.0 — единая аудиомедиатека

- медиатека разделена на два логических уровня: **«Песни»** для классических раундов и **«Аудио»** для любых самостоятельных треков;
- добавлена сущность `MediaTrack`: она содержит внутреннее название и ссылку на физический `AudioAsset`, но не требует исполнителя, названия песни, минуса или плюса;
- `Song` теперь хранит исполнителя/название и ссылки `minusTrackId` / `plusTrackId` на переиспользуемые медиатреки;
- `AudioAsset` по-прежнему является content-addressed Blob (`id === SHA-256`), поэтому один физический файл хранится в IndexedDB только один раз, даже если на него ссылаются несколько `MediaTrack`;
- при создании обычной песни минус и плюс можно либо загрузить как новые медиатреки, либо выбрать из уже существующего раздела «Аудио»;
- самостоятельный аудиотрек можно создать без `Song` — это база для межраундов, заставок, фрагментов, mashup, речи и любых других аудиозаданий;
- у `MediaTrack` можно переименовать внутреннее название и заменить физический файл, сохранив ID трека и все ссылки на него;
- удаление песни больше не удаляет связанные медиатреки: они остаются доступными в общей аудиобиблиотеке;
- удаление медиатрека разрешено только когда на него не ссылается ни одна песня; физический Blob удаляется только если больше нет других треков с тем же `audioId`;
- IndexedDB обновлён отдельным store `media-tracks`; существующие песни со старыми `minusAudioId` / `plusAudioId` автоматически мигрируются при первом запуске;
- начиная с v1.4 формат содержит `tracks.json`; последующие версии формата расширяют игровую структуру, при этом старые архивы продолжают автоматически мигрироваться;
- экспорт всей медиатеки включает и свободные аудиотреки, не привязанные ни к одной песне — они не потеряются при резервном копировании.

Текущая модель данных:

```text
Question -> Song -> MediaTrack -> AudioAsset (SHA-256 -> Blob)
                    ^
InterRound ---------+
```

## Усиление хранения и импорта/экспорта после ревью

- аудио переведено на content-addressed хранение: `AudioAsset.id` равен SHA-256 содержимого, поэтому одинаковый файл физически хранится в IndexedDB один раз независимо от способа добавления;
- старые аудиозаписи с `audio-*` идентификаторами автоматически мигрируются на SHA-256 при загрузке базы; старые ссылки песен преобразуются в `MediaTrack`, дубликаты Blob удаляются;
- SHA-256 вычисляется при добавлении аудио один раз, а не для всей существующей медиатеки при каждом импорте; для крупных Blob SHA/CRC считаются в Web Worker;
- перед сохранением нового аудио проверяются сигнатура формата и способность браузера прочитать metadata; импорт выполняет ту же проверку;
- импорт и экспорт используют единый строгий контракт структуры игры и песен, ограничения размеров/строк, валидные timestamps и контроль ссылок;
- ZIP-парсер отклоняет ZIP64, multi-disk, шифрование, data descriptor, дубли путей, рассинхронизацию local/central headers и выходы данных за границы контейнера; SHA-256 и CRC проверяются для всех заявленных файлов, включая `manifest.json`;
- preview импорта больше не является готовым snapshot состояния: при подтверждении merge пересчитывается относительно актуальной медиатеки, что исключает потерю параллельных пользовательских изменений;
- обычное автосохранение стало инкрементальным по сущностям и сериализованным; полный `clear + rewrite` используется только для миграционных сценариев;
- IndexedDB хранит `state-revision`. Конфликт двух вкладок переводит устаревшую вкладку в заблокированный режим и не позволяет ей затереть новую ревизию; вкладки дополнительно уведомляются через `BroadcastChannel`;
- при ошибке первичной загрузки редактор не открывается с пустым state. Последние изменения дополнительно flush-ятся при уходе страницы в background/`pagehide`;
- сохранённые сессии приводятся к текущей структуре после редактирования игры: удалённые команды/вопросы очищаются, отсутствующие score восстанавливаются;
- продолжение партии проверяет только ещё не сыгранные вопросы, поэтому удалённое аудио уже завершённого вопроса не блокирует продолжение;
- в настройках показывается фактическое использование browser storage/quota и доступна явная просьба браузеру о persistent storage;
- для общей песни показывается предупреждение о влиянии на несколько игр и доступно создание отдельной копии песни;
- версия приложения для manifest берётся из `package.json` через Vite, отдельная вручную синхронизируемая строка удалена.

Подробная карта исправлений находится в `REVIEW_FIXES.md`.

## Экспорт и импорт (добавлено в v1.2.0)

### Экспорт отдельной игры

На карточке каждой игры появилась кнопка **«Экспортировать игру»**.

Создаётся файл с расширением `.melody`, который содержит:

- настройки выбранной игры;
- раунды, категории, вопросы и команды;
- только те песни из общей медиатеки, которые используются этой игрой;
- только `MediaTrack`, на которые ссылаются эти песни;
- физические аудиофайлы, используемые этими медиатреками.

Текущая игровая сессия (баллы, сыгранные карточки, текущий раунд и штрафы) специально не экспортируется. Импортированная игра всегда готова к новой партии.

### Импорт игры

На экране **«Мои игры»** появилась кнопка **«Импортировать игру»**.

Перед изменением данных приложение:

1. открывает архив;
2. проверяет версию формата;
3. проверяет обязательные файлы;
4. сверяет размеры;
5. проверяет SHA-256 каждого файла;
6. проверяет CRC ZIP-записей;
7. анализирует песни и аудио относительно текущей медиатеки;
8. показывает сводку импорта.

Если игра с тем же постоянным `gameId` уже существует, можно выбрать:

- **Заменить существующую** — обновить конфигурацию этой игры и начать новую сессию;
- **Импортировать как копию** — оставить существующую игру и создать новую с новым `gameId`.

Совпадение по одному названию игры конфликтом не считается.

### Дедупликация песен и аудио

При импорте отдельно сопоставляются три уровня:

- физические `AudioAsset` — по SHA-256 содержимого;
- `MediaTrack` — по внутреннему названию и SHA-256 связанного аудио;
- `Song` — по нормализованным исполнителю/названию и уже сопоставленным `minusTrackId` / `plusTrackId`.

Если тот же MP3 уже есть в медиатеке, второй Blob в IndexedDB не создаётся. Один физический файл при этом может использоваться несколькими медиатреками с разным смыслом/названием.

### Экспорт и импорт всей медиатеки

На экране **«Медиатека»** появились кнопки:

- **«Экспортировать медиатеку»**;
- **«Импортировать медиатеку»**.

Экспорт создаёт `.melody-library` со всеми песнями, всеми `MediaTrack` (включая свободные, не связанные с песнями) и необходимыми физическими аудиофайлами. Импорт работает как merge на всех трёх уровнях и не копирует одинаковые Blob повторно.

### Формат архива

`.melody` и `.melody-library` являются ZIP-совместимыми контейнерами без повторного сжатия аудио. MP3/WAV/OGG уже являются большими бинарными файлами, поэтому приложение не пытается держать дополнительно сжатую копию каждого трека в памяти.

Пример структуры `.melody`:

```text
manifest.json
game.json
songs.json
tracks.json
audio/
  <sha256>.mp3
  <sha256>.mp3
```

`manifest.json` содержит `formatVersion`, версию приложения, дату экспорта и SHA-256 каждого файла. Это позволяет в дальнейшем мигрировать старые архивы и обнаруживать повреждение до записи данных.

### Транзакционный импорт

После проверки приложение сначала формирует итоговое состояние целиком, затем сохраняет игры, песни, аудио, сессии и служебные данные одной IndexedDB-транзакцией. Только после успешной записи новое состояние применяется в Effector.

Повреждённый или неподдерживаемый архив не должен оставлять базу в частично импортированном состоянии.

## Хранение рабочего состояния

Рабочие данные по-прежнему находятся в IndexedDB:

- `games` — конфигурации игр;
- `songs` — песни классических раундов: исполнитель, название и ссылки на минус/плюс;
- `media-tracks` — общая библиотека переиспользуемых аудиотреков;
- `audio` — физические content-addressed Blob-файлы по SHA-256;
- `sessions` — игровые сессии;
- `meta` — служебные данные.

Экспорт теперь даёт переносимую резервную копию конкретной игры или всей медиатеки, поэтому IndexedDB больше не является единственной копией подготовленного контента.

- одна песня может использоваться в нескольких играх;
- отдельная игровая сессия для каждой игры;
- продолжение незавершённой игры;
- неправильный ответ блокирует команду до конца текущей песни и исключает её из следующей песни на один розыгрыш;
- «Никто не угадал» включает плюс без начисления очков;
- ручная корректировка баллов;
- автоматический переход между раундами.

## Проверка

```bash
npm run build
npm test
```

Тесты покрывают:

- экспорт и восстановление игры с аудио;
- повторный импорт той же игры без дублирования песен и Blob-файлов;
- экспорт/импорт медиатеки и дедупликацию внутри одного архива;
- повреждённые ZIP-контейнеры и изменённые байты;
- строгую и draft-safe валидацию модели;
- восстановление устаревшей игровой сессии;
- базовую проверку сигнатур аудиофайлов.

### Текущее ограничение размера

Экспорт использует ZIP32 без сжатия, поэтому один `.melody` / `.melody-library` должен быть меньше 4 ГБ. Для стартовой локальной версии этого обычно достаточно; при росте медиатеки выше этого размера следующий шаг — ZIP64/потоковая запись через desktop-оболочку или File System Access API.
